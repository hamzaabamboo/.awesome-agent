# Trash

Treat the current design direction as rejected. Replace its composition and interaction presentation while retaining the complete product contract. A wording, color or spacing patch does not satisfy this request.

## 1. Recover the contract

Run `get-your-shit-together`, then `what-did-i-say`, under the project's task-record rules. Reconcile the complete current-session request stream, supplied references and latest correction before proposing a replacement. Keep earlier functions, controls, content, states, accessibility, responsive behavior and explicit constraints binding unless the user explicitly superseded them.

Inspect the current source and actual rendered artifact. Inventory its functions and states, including expanded controls and less-visible flows. Put a compact preservation checklist and the observed design failures in the canonical task record. Distinguish a missing requirement from an unknown fact; resolve available evidence yourself. Preserve unrelated work and a recoverable baseline using existing project conventions. Scrapping the direction does not authorize deleting files, history or user data.

## 2. Reset the design direction

Evaluate the full installed design-skill catalog against the deliverable. Read and execute every applicable skill and its required references, covering visual hierarchy, domain/task flow, typography, content, density, accessibility, responsive layout, motion and the project's implementation stack. Use all applicable expertise, not a favorite preset. Resolve conflicting recipes against the brief, references, product semantics and established constraints; do not pile incompatible styles together.

If the available skills cannot address a demonstrated gap, use `find-skills` to research a suitable skill within the current task's research permissions. Explain the gap and candidate fit. Discovery does not authorize installation, paid services, uploads or outbound reporting; continue with available capabilities when those actions are not authorized.

Develop 2–3 materially different viable compositions and present them for the user to choose, combine or narrow before implementing a replacement. Show comparable inspectable sketches/mockups using the real task content and retained functions, with narrow-screen structure and reference-backed motivation/tradeoffs. Compare hierarchy, grouping, density, navigation and primary actions; palette swaps or names alone are not alternatives. Refine the user's selection as requested. Wait for their direction choice unless they already selected it or explicitly delegated selection; resolve ordinary implementation choices yourself afterward. Make the direction specific to the subject matter and references, not arbitrary novelty, invented data or a familiar aesthetic applied to every product.

Before implementation, record the motivation for each material replacement: decision → requirement or observed task problem → inspected evidence → expected benefit. Follow the shared design-decision gate. Rejection motivates replacing the failed axes, not inventing requirements or changing working features. Personal taste and novelty alone do not justify a direction. Give independent council this rationale and require it to check the rendered replacement against the same constraints; test hypothesized benefits rather than present them as facts.

UIZZE reference research is a required stage, not optional inspiration. Before choosing those directions, execute `ui-radar` using the shared design-routing rule: focused query, actual relevant screenshots, canonical sources and decisions informed. Supplied authoritative references retain priority but do not waive this research unless the user explicitly skips it. App icons, marketing screenshots for an in-app-layout question, skill loading and search metadata alone do not satisfy the stage. If the bounded free lookup yields no usable screen, record the concrete gap and continue from project evidence without fabricating references or reference-backed acceptance.

## 3. Rebuild

Implement the selected replacement in the project's existing stack. Rework the responsible layout/component structure rather than layering cosmetic overrides onto the rejected composition. Preserve the function/state inventory and real data boundaries. Reuse working behavior and suitable primitives; a visual redo is not permission to rewrite unrelated business logic.

Continue through implementation and verification. A plan, mood board, skill list or audit alone is not the requested replacement. If the invocation is part of creating or evaluating this skill rather than an actual product task, keep that distinction explicit and do not invent a product to redesign.

## 4. Prove and independently council

Inspect the replacement in the project's canonical real browser or rendering harness at relevant desktop and narrow sizes. Exercise the affected normal, expanded, empty, loading/error, keyboard and persistence states. Apply `break-ui` to data-bearing layouts after normal-state checks, within fixture/data permissions. Compare the preservation inventory and rendered result with the baseline and authoritative references. Fix defects and inspect again.

Invoke `the-council` with a separate independent agent for every audit and every redesign, including this workflow. Give the reviewer the actual current artifact, complete requirements and preservation inventory without a preferred verdict or your proposed findings. A self-review, multiple roles played by one agent, or the builder repeating its own verdict does not satisfy independence. For visual judgments, the reviewer must inspect the rendered artifact; source alone cannot establish visual acceptance.

Check every reviewer finding yourself against the source or runtime, fix confirmed defects, and obtain fresh independent review of the changed artifact. If an independent agent or required runtime is unavailable, complete all unaffected work and report that exact unmet gate honestly. Do not substitute self-certification or report council approval.

## Completion

Complete only when the replacement is materially different on the rejected axes, every retained function and constraint is accounted for, affected runtime states have been exercised, and independent council findings are resolved. User acceptance remains the user's decision; neither reviewer agreement nor a self-score establishes it.

Report the concrete structural changes, preserved capabilities, actual checks and independent review result, and the visible artifact location. Keep measurements, provider tokens and costs separate; unavailable values stay unknown. Keep the canonical task record current, close owned temporary resources, and preserve the project's permissions for commits, pushes and external writes.
